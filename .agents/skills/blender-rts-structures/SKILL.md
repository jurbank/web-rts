# Blender RTS structures

Every structure belongs to a theme, such as `modern` or `cyberpunk`. If the request doesn't name one, ask. Read `docs/ART_DIRECTION.md` first for the rules every theme follows, then `docs/themes/<theme>.md` for the theme's shape language, palette, glow, signage, and building types. The theme file decides the look. A building that would fit another theme has failed, even if it passes every check. If the theme has no file yet, write one with the user before modeling. Read [the project pipeline](references/pipeline.md) for source and export paths, Blender conventions, and helper commands. Resolve paths from the web-rts workspace root. For an asset revision, open its existing source first and preserve its asset ID, anchor, and intentional dimensions.

## Build the asset

1. Establish the structure's role, faction or visual family, world-space footprint, main entrance or front, and any required moving parts. Take gameplay dimensions from the matching project definition or placement rules when available. When none exist, record provisional dimensions in the source collection and describe the assumption when delivering.
2. Take the building type's row from the theme file: its signature silhouette, accent, and required elements. Pick neighbors to line up beside it from the same theme only. Match their scale and detail density, except where they break the theme file. Give the structure its own silhouette and accent unless it is a designated variant. When the theme has no approved buildings yet, build one at a time without neighbors, and treat the look as provisional until the user approves it.
3. Block out the footprint, primary mass, and one or two features that identify the role from above, using the theme's shape language. Export with `--blockout` and render it with `--with` the neighbors to check the silhouette, the roof, and the front from the game camera before adding detail. Reuse matching modular geometry where it already exists.
4. Texture the asset with its theme's atlas, as the pipeline describes. Read `art/blender/materials/themes/<theme>/atlas.json` to choose cards rather than viewing the atlas, and map faces onto cards with `scripts/atlas_cards.py` instead of writing UV code. Add a card when the theme's atlas has nothing that fits the theme file. Paint glow on the glow map where the theme allows it. Painted detail replaces modeled detail. Flat colors are for blockouts only. Use Blender's own Python and numpy for any other image work instead of installing packages.
5. Save the editable model in its canonical source file. Put the render meshes for the default state in the named asset collection, with helpers and experiments in sibling collections. Mark the render collection as an Asset and give it a useful description. Keep procedural modeling modifiers editable in the source.
6. Export the asset without `--blockout`. The export fails when the GLB carries no image textures, or no glow in a theme that glows. Report the export's size, triangles, primitives, and textures, and compare them with neighboring assets and the expected repetition on a typical map.
7. Render the export next to its closest neighbors and have it reviewed as [the review guide](references/review.md) describes. Fix what the review finds, then export, render, and review again until the verdict is ship.
8. Rebuild the gallery whenever you add, remove, or rename an asset, after saving its source.
9. Deliver the review sheet and the export summary, and leave the GLB in staging. A ship verdict means the asset is ready for the user to look at. Copy it to `apps/website/public/models/structures/themes/<theme>/` only when the user approves it.

Keep terrain, selection overlays, and gameplay collision or navigation in their existing project systems. Use the Blender connector for an existing scene when helpful, or Blender's background CLI with `bpy` for repeatable modeling, export, rendering, and verification.
